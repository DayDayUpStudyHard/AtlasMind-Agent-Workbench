# 合同作业系统六层架构设计记录

> 日期：2026-08-08  
> 目标：把 AtlasMind Contract Agent 从“合同问答 / 报告生成工具”推进为“合同作业系统”。  
> 当前落点：合同画像、履约日程、风险审查、证据核验共用同一套解析、证据、运行、校验和人工复核链路。

## 1. 设计原则

1. 基础合同事实少量固定，保证所有合同都有统一入口。
2. 合同类型专属要素不在前端或规则里硬编码，由 LLM 基于合同原文动态发现。
3. 要素、风险、履约不能各自重新解析合同，应共用文档解析和证据快照。
4. LLM 负责理解、归纳、解释和建议，系统负责证据、引用、状态、版本、校验和人工确认。
5. 前台只显示重点，完整原文、页码、段落、引用和 Agent 运行路径可展开追溯。
6. 管理端保留完整可观测性：运行类型、图节点、工具调用、输入输出、错误、fallback 和人工介入点。

## 2. 六层架构

### L1 合同入口与文档解析层

负责合同创建、文件上传、文字/PDF/DOCX/DOC 解析、OCR/MinerU 质量兜底、条款切分、页码段落定位。

输出：

- `contract_case`
- `contract_document`
- `contract_clause`
- `contract_clause_chunk`
- 文档处理 Job 和 Trace

要求：

- 解析质量低时系统自动升级解析方式，不把“解析器质量差”直接丢给用户。
- 原文中的噪声、乱码和 OCR 异常需要保留诊断，但不能直接作为正式履约依据。
- 所有后续 Agent 都从这一层拿合同证据，不重复读文件。

### L2 证据快照与混合检索层

负责把合同条款、知识库、规则库和用户上传履约证据转成可检索证据。

输出：

- 证据快照 hash
- 合同条款引用
- 知识库引用
- 履约证据引用
- 向量检索 + 关键词检索 + 规则候选的融合结果

要求：

- Elasticsearch 可用时使用混合检索和规则候选交叉验证。
- Elasticsearch 不可用时降级为关键词和规则候选，但要在 Trace 中记录 fallback。
- 知识库是一等证据来源，不是最后兜底；风险审查和履约核验都必须查知识库。

### L3 Planner + Harness + LangGraph 状态执行层

负责任务规划、工具调用、图状态推进、Checkpoint、Resume、人工中断和失败恢复。

核心能力：

- `CONTRACT_ELEMENT_EXTRACTION`：合同画像与事实快照。
- `CONTRACT_REVIEW`：风险审查。
- `FULFILLMENT_CHECK`：履约核验。
- 每个任务按 `task_type -> graph_name` 路由到独立 Graph Adapter。

要求：

- Agent Run 必须记录运行目的：是在做要素提取、风险审查、履约核验还是版本复核。
- 每个图节点都写入 observation，包括工具名、证据数量、模型、prompt/schema 版本、fallback 原因。
- WAITING_HUMAN 不得写成 COMPLETED。

### L4 合同画像、风险、履约业务 Agent 层

把底层证据加工成用户真正要处理的业务对象。

合同画像：

- 基础字段固定：标题、类型、甲方、乙方、我方角色、金额、签订日期、生效日期、结束方式等。
- 专属字段由 LLM 动态发现：工程合同可出现工程地点、规模、设计标准、技术指标、交付规范；信息技术合同可出现 SLA、系统范围、接口、数据交付等。
- 每个字段必须带连续原文引用。

风险审查：

- 领域维度由任务和证据决定，不固定死法律、知识产权、环保等标签。
- 输出尽量详细，前端只展示摘要、影响、首要处理、证据和可展开详情。

履约核验：

- 放在时间节点详情内，不做复杂履约状态体系。
- AI 只做“合同要求 -> 证据 -> 判断 -> 缺口”分析，不自动判定最终完成/失败。
- 最终结果必须人工确认。

### L5 确定性校验、引用校验与质量门禁层

负责阻止模型“看起来合理但证据不成立”的输出进入正式结果。

校验项：

- JSON Schema / Pydantic 结构校验。
- 引用 quote 必须逐字存在于证据条款。
- 必需项必须有合同原文依据。
- 辅助建议不能冒充合同约定。
- 规则评分、状态、证据 hash 由系统计算，不由 LLM 决定。

失败路径：

- 首次校验失败进入 repair 节点。
- repair 后仍失败，生成有限报告或待人工确认结果。
- 不得把 INVALID 结果直接持久化为正式报告。

### L6 合同作业工作流与人工复核层

把 Agent 输出变成可处理、可追踪、可关闭的工作项。

前台：

- 合同详情页显示合同画像、履约日程、风险研判、原文证据和基础 Agent 运行信息。
- 用户可以上传修改后的合同、履约证明、付款记录、报告、图片等证据。
- 用户可确认字段、处理风险、接受例外、复核节点、查看历史。

管理端：

- AI Observability 显示每次 Agent 调用的详细路径、工具调用、图节点、trace、错误和产物。
- 系统日志记录知识库范围变更、Agent 失败、fallback、人工确认。

## 3. 当前实现落点

本次实现把合同画像接入要素提取图：

- 新增 `contract_profile` / `profile_validation` 图状态。
- `build_contract_profile` 节点调用 LLM 生成动态画像。
- `contract_extraction_snapshot.profile_json` 保存画像 JSON。
- 前端合同要素区优先展示 `contractProfile.baseFields + contractProfile.groups`。
- 没有画像时继续使用旧 `contractElements` 兜底。

## 4. 后续演进顺序

1. 完善合同画像字段确认：支持人工确认、修改、忽略和引用复核。
2. 风险审查改为优先消费画像 + 原文证据 + 知识库，再生成细分风险。
3. 履约核验改为按节点拆分子要求，并绑定证据快照。
4. 管理端评测集覆盖画像准确率、引用准确率、风险召回率和履约判断一致性。
5. 引入第二模型核验前，先把当前六层链路跑通并建立评测基线。
