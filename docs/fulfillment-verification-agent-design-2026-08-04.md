# 合同履约核验 Agent 设计记录

**记录日期**：2026-08-04  
**状态**：方案已确认，待分阶段实现  
**适用产品**：AtlasMind 企业合同全生命周期运营 Agent

## 1. 方向

合同时间线不应只负责提醒日期，还要在节点到达后继续判断履约是否完成、材料是否充分、是否能够通过验收，以及是否存在逾期、拒付、解除或争议风险。

产品能力从：

> 提取合同时间节点并提醒

升级为：

> 基于合同义务、履约证据和验收标准，辅助判断履约状态与验收风险的 Agent。

## 2. 甲乙方视角

### 2.1 甲方视角

判断乙方是否已经按照合同要求完成交付或服务，包括：

- 是否按约定时间完成；
- 是否交付了合同约定的成果物；
- 报告、数据、图片、验收单等材料是否齐全；
- 交付内容是否满足合同中的数量、质量、技术指标和验收标准；
- 是否存在逾期、整改未闭环或付款前置条件未满足；
- 是否需要补充材料、发起整改或拒绝验收。

### 2.2 乙方视角

判断当前材料是否足以支持甲方验收，包括：

- 是否完成合同约定的工作内容；
- 是否准备齐全报告、测试数据、施工图片、交付清单等证据；
- 是否满足甲方验收条件；
- 哪些材料缺失可能导致验收延期或付款延迟；
- 哪些内容存在被甲方质疑、要求整改或拒收的风险；
- 在正式提交验收前还需要补充什么。

## 3. 履约核验输入

履约核验不能只依赖合同正文，需要形成一个“节点履约证据包”：

- 合同正文及当前版本；
- 合同条款和履约义务；
- 付款记录和发票；
- 技术报告、交付报告和成果物；
- 测试数据、检测记录和验收单；
- 施工现场图片、视频或其他现场记录；
- 交付清单、签收记录和整改记录；
- 邮件、通知、会议纪要和双方确认信息；
- 用户手动补充的事实和备注；
- 企业制度、验收标准、合同模板和条款知识库。

所有证据都要保留来源、文件版本、上传时间、页码或文本片段，便于追溯。

企业知识库不是最后兜底，而是合同审查和履约核验的一等证据来源。合同风险检查时要同时检索合同原文、内置标准条款和管理端上传的企业知识库文档；履约核验时也要检索企业验收制度、付款制度、模板和历史规范，将其作为判断证据的一部分。

## 4. Agent 输出

每次履约核验应输出结构化结果，而不是只生成一段总结：

### 4.1 结论状态

- 符合合同要求；
- 不符合合同要求；
- 证据不足，无法判断；
- 存在较高验收风险；
- 合同条款或验收标准不明确；
- 待人工复核。

### 4.2 结论依据

- 对应合同条款；
- 合同要求完成的动作；
- 已找到的履约证据；
- 证据与合同要求的对应关系；
- 缺失的证据；
- 发现的差异和问题；
- 证据时间是否落在合同期限内；
- 责任方和相关协作方；
- AI 置信度；
- 是否需要人工复核。

### 4.3 示例

> **结论：暂不能确认验收通过**  
> 已发现：已上传技术报告 1 份。  
> 缺失证据：合同要求的现场验收记录、测试数据、整改闭环证明。  
> 风险：甲方可能以材料不完整为由暂缓验收或付款。  
> AI 置信度：62%。  
> 状态：待人工复核。

## 5. 时间节点与基准日期

### 5.1 相对期限

合同中的“签订合同后180天内”“生效后30天内”“收到发票后10日内”等内容，必须识别：

- 原文期限；
- 基准事件；
- 基准日期；
- 计算后的截止日期；
- 计算依据；
- 日期是否由用户确认。

例如：

> 合同签订后180天内  
> 基准事件：合同签订日  
> 基准日期：2025-08-15  
> 截止日期：2026-02-11  
> 计算依据：2025-08-15 + 180个自然日

### 5.2 多个候选基准日期

如果合同中存在多个可能的签订日、生效日或其他基准日期：

- 不自动选择；
- 不计算多个截止日期；
- 前台显示“基准日期待确认”；
- 列出候选日期及其原文依据；
- 用户在前台选择正确日期；
- 用户确认后重新计算并保存截止日期。

### 5.3 缺少基准日期

如果无法找到基准日期：

- 仍然显示相对期限；
- 明确显示缺少的基准日期；
- 截止日期显示“待计算”；
- 不猜测、不使用上传日期、不使用当前日期代替。

示例：

> 合同签订后180天内  
> 缺少基准日期：合同签订日  
> 截止日期：待补充合同签订日后自动计算

## 6. 节点后果展示

### 6.1 合同明确后果

合同原文明确写出的后果应直接展示，例如：

- 逾期违约金；
- 暂缓付款；
- 要求整改；
- 拒绝验收；
- 解除合同；
- 赔偿损失；
- 免责条件；
- 续签或终止条件。

这类内容标记为：

> 合同原文明确约定

并展示对应条款和原文片段。

### 6.2 AI 推断后果

当合同没有明确写出后果，但根据当前证据可能产生业务风险时，可以展示 AI 风险提示，例如：

> AI 可能后果：材料不完整可能导致验收延期或付款延迟。

这类内容必须单独标记：

> AI 推断，仅供参考，不代表合同约定

AI 推断不得写入“合同明确责任”，不得替代法律意见，也不能自动改变合同状态。

建议默认折叠 AI 推断内容，用户点击“查看 AI 风险提示”后展开。

## 7. 节点状态

时间节点采用以下状态：

- 待确认；
- 待开始；
- 进行中；
- 已完成；
- 已逾期；
- 完成失败。

规则：

- 日期到达且没有人工确认完成时，可以自动标记为“已逾期”；
- “已完成”和“完成失败”不能仅靠日期自动判断；
- AI 只能给出建议结论；
- 最终履约状态由用户确认；
- 用户确认时应填写备注，后续可要求上传对应证据。

## 8. 人工确认边界

MVP 阶段：

- Agent 自动提取履约义务；
- Agent 自动收集和匹配证据；
- Agent 自动发现缺项、冲突和风险；
- Agent 给出履约或验收建议；
- 用户手动标记“完成”或“失败”；
- 用户填写确认备注并可关联证据。

Agent 不得在 MVP 阶段自动执行以下动作：

- 自动确认验收通过；
- 自动确认合同履约完成；
- 自动确认履约失败；
- 自动发起拒付、索赔、解约或其他高风险法律动作。

## 9. 不确定性与错误边界

系统必须明确告诉用户：

- 没有找到证据；
- 证据不完整；
- 证据与条款无法对应；
- 多个基准日期无法确定；
- 合同条款存在歧义；
- AI 结论置信度较低；
- 判断结果容易受到证据质量影响；
- 当前结论需要人工复核。

推荐将判断结果拆为：

1. 已确认事实；
2. 合同明确要求；
3. 已找到的证据；
4. 缺失或冲突证据；
5. AI 判断；
6. AI 可能风险；
7. 人工确认结果。

这样用户可以区分“合同写了什么”“系统找到了什么”和“AI 推测了什么”。

## 10. MVP 展示边界

MVP 阶段不单独建设完整的履约管理看板，也不引入过多新的履约状态字段。

履约核验结果先放在合同时间节点详情中，与当前节点信息一起展示：

- 节点日期或相对期限；
- 基准日期和计算依据；
- 原文依据；
- 合同明确要求；
- 已找到的履约证据；
- 缺失证据；
- 合同明确后果；
- AI 推断风险；
- Agent 核验结论；
- AI 置信度；
- 人工最终确认结果。

这样用户进入合同详情后，可以直接在时间线中看到每个节点的提醒、证据、风险和核验结论，不需要跳转到另一个复杂模块。

后续当履约数据、证据记录和核验任务足够多时，再独立建设履约模块或履约看板，支持：

- 按合同查看全部履约义务；
- 按责任方查看待办；
- 按风险等级筛选节点；
- 按逾期、待补证、待复核聚合任务；
- 统一查看核验历史和整改闭环。

当前阶段的原则是：

> 先把履约核验嵌入时间节点详情，保证信息可用、可追溯、可人工确认；后续再从详情页中抽象出独立履约运营能力。

## 10.1 当前 MVP 落地边界

本轮先落地“合同时间节点级履约核验”：

- 只对文档解析流水线产生的真实时间节点发起核验，因为这些节点有 `contract_timeline_node.id`，可以稳定保存历史；
- 前台在合同详情页的时间节点卡片内发起履约核验；
- Java 负责创建 `FULFILLMENT_CHECK` Agent Run，并创建 `contract_fulfillment_check` 待处理记录；
- Python Agent Runtime 执行 `getContractCase → listContractTimeline → searchPolicyKnowledge → verifyFulfillmentEvidence` 等工具调用；
- 核验产物保存到 `contract_fulfillment_check`，包含结论、风险等级、可信度、合同要求、证据快照、缺失证据、合同明确后果和 AI 推断风险；
- 前台展示最新核验结果和历史记录；
- 人工确认必须填写说明，AI 不自动把节点改成完成或失败。

暂不做独立履约看板、自动提醒升级、证据多对多绑定和多用户权限控制。这些能力进入后续履约运营阶段。

## 11. 后续实现阶段

### 阶段一：时间节点可信化

- 优化基准日期识别；
- 多候选日期前台选择；
- 缺失基准日期明确提示；
- 计算并展示年月日；
- 展示日期计算依据；
- 清理内部技术标签。

### 阶段二：履约义务结构化

- 将节点扩展为履约义务；
- 提取责任方、完成动作、交付物和验收标准；
- 保存合同条款与证据引用；
- 支持甲方和乙方视角。

### 阶段三：履约证据核验

- 上传报告、图片、付款记录和验收材料；
- Agent 将证据匹配到具体义务；
- Agent 检索企业知识库中的验收制度、付款制度、模板和历史规范；
- 识别缺失、逾期、冲突和不符合项；
- 输出可追溯的核验报告。

### 阶段四：验收风险评估

- 评估是否可能通过验收；
- 识别付款延迟、整改、违约和争议风险；
- 同时输出合同明确后果和 AI 推断风险；
- 低置信度结果自动进入人工复核。

### 阶段五：履约持续运营

- 节点提醒；
- 逾期升级；
- 整改闭环；
- 证据持续补充；
- 人工确认历史；
- 履约状态和风险变化追踪。

## 12. 核心原则

1. 不把相对期限误当成确定日期。
2. 不在多个候选日期中替用户猜选。
3. 不把 AI 推断当成合同原文。
4. 不用模板化描述替代具体合同事实。
5. 所有结论都必须能追溯到条款和证据。
6. AI 负责分析和提示，用户负责最终确认。
7. 无法判断时明确显示“无法判断”，而不是生成确定答案。
