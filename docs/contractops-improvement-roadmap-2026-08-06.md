# AtlasMind ContractOps 完善与未来发展方案

> 日期：2026-08-06  
> 规划周期：90 天 MVP 增强 + 6 个月企业化  
> 评估依据：当前仓库实现、现有 PRD，以及用户提供的“智慧合同评审”方案截图  
> 说明：截图只能反映对方展示出的产品能力，不能代表其真实实现深度。

## 1. 核心结论

AtlasMind 不应复制成另一个“合同评审助手”。当前项目已经具备合同案件、智能录入、审查规则、标准条款、风险评分、版本对比、履约义务、证据核验、审批动作、Agent 运行追踪和评测中心等基础，能力范围已经超过截图所表达的“归档 + 评审 + 问答”。

更合适的定位是：

> 面向企业法务、采购和业务团队的合同风险与履约闭环运营平台。

未来竞争力不应来自“接入了多少模型”，而应来自四件事：

1. 每个判断都能回到合同原文和企业制度；
2. 风险审查准确率可以被数据证明；
3. 审查结果能进入修改、审批、签署和履约流程；
4. 企业可以控制知识、权限、模型、数据和审计记录。

## 2. 当前项目真实基线

### 2.1 已具备的优势

| 能力 | 当前情况 | 判断 |
|---|---|---|
| 合同案件与组合管理 | 已有案件、状态、驾驶舱、工作队列和时间线 | 已超过单点评审工具 |
| 智能录入 | 支持文本及 TXT、MD、PDF、DOC、DOCX，包含字段提取、原文引用和人工确认 | 基础完整，需增强解析可信度 |
| 合同审查 | 已有 19 条规则、5 维评分、一票否决、风险发现和双引用 | 是当前最有价值的核心能力 |
| Agent Runtime | 已有 LangGraph 审查图、确定性规则、检索、校验、Reflection、有限补证、报告持久化 | 技术方向正确，不需要推倒重做 |
| 知识与条款 | 已有知识空间、合同使用范围、标准条款库和历史决策检索入口 | 缺少法规治理和知识版本体系 |
| 履约运营 | 已有义务、时间节点、证据核验、人工确认和历史记录 | 形成差异化的关键方向 |
| 可观测与评测 | 已有 Run、Trace、Tool Call、可观测页面、评测中心和发布阈值代码 | 评测样本仅为起步规模 |
| 安全边界 | 高风险动作需要人工批准，LLM 不直接决定最终分数和履约结果 | 适合法务场景 |

### 2.2 当前主要短板

| 短板 | 现状表现 | 业务影响 |
|---|---|---|
| 解析证据不够稳定 | 已有 PDF 质量检测及 AUTO/FAST/MINERU/OCR 路由，但页级质量、选择原因和 canonical text 关系尚未完整沉淀 | 错字、表格和扫描页会污染后续结论 |
| 评测集太小 | 当前内置评测集只有少量样例 | 不能证明重大风险召回率和误报率 |
| 法规知识治理不足 | 有通用知识库，但缺少法规效力层级、生效时间、废止状态、适用地区和引用版本 | 法律依据可能过期或适用错误 |
| 审查交付体验不够产品化 | 能生成发现和报告，但缺少法务常用的一页总览、逐条处置、修改稿和导出交付 | 能力强但用户感知弱 |
| 合同问答边界不够鲜明 | 已有 ChatWindow，但合同范围、引用、版本和拒答规则需要强化 | 容易退化成普通问答 |
| 企业权限尚未闭环 | 有登录和操作者字段，但组织级 RBAC、职责分离、租户隔离尚不完整 | 难以进入真实企业试点 |
| 模型部署能力不足 | 当前以外部 DeepSeek 兼容 API 为主 | 无法直接满足部分客户的本地化和数据不出域要求 |
| 效果指标缺少真实基线 | 驾驶舱有业务数据，但尚未形成审查耗时、采纳率、误报率和风险闭环率 | 难以证明 ROI |

## 3. 与截图方案的对标

| 截图能力 | AtlasMind 当前情况 | 建议 |
|---|---|---|
| 合同归档助手 | 已有案件、文件版本、字段提取和组合驾驶舱 | 增加批量导入、统一检索、重复合同识别和归档分类 |
| 合同评审助手 | 已有规则、风险评分、双引用、报告和审批 | 重点完善审查工作台、修改建议、处置闭环和报告导出 |
| 智能问答 | 已有对话入口和知识检索 | 改为严格的案件/版本作用域问答，答案必须引用，证据不足时拒答 |
| 合同分类、要素抽取、金额计算 | 已基本覆盖 | 增加表格字段、金额组成、税率、付款条件和跨字段一致性校验 |
| 法条搜索 | 有知识库检索底座 | 建立法规库、效力与版本元数据、适用范围和引用快照 |
| 风险识别 | 已有更强的确定性规则 + LLM 语义判断 | 用 Golden Dataset 证明准确率，避免只展示规则数量 |
| PDF、图片、DOCX 解析 | PDF/DOC/DOCX 已有，PDF 有 OCR/MinerU 路由；图片入口不完整 | 先做好扫描 PDF 和表格，之后增加 JPG/PNG 与版面定位 |
| 本地模型底座 | 当前主要调用外部模型 | 建立模型网关，支持云模型、私有 API 和本地模型按客户切换 |
| 合同模板、法规、合同文本知识 | 已有标准条款和通用 KB | 升级为有版本、效力、范围和审批流程的法律知识资产 |
| 管理、评审、风控成效 | 有 KPI 和队列基础 | 增加真实基线、节省工时、采纳率、风险关闭率和逾期降低率 |

结论：截图适合作为产品展示结构参考，不适合作为技术路线参考。AtlasMind 最值得补的是“可信度、交付体验和企业落地”，不是再堆一层功能名词。

## 4. 目标产品结构

```text
合同入口层
  批量归档 / 智能录入 / 文件版本 / 合同检索 / 案件级问答
        ↓
可信文档层
  PDF/DOCX/图片/表格解析 / 页级质量门禁 / canonical text / 可定位引用
        ↓
合同智能层
  条款分类 / 要素抽取 / 确定性规则 / 语义审查 / 混合检索 / 风险评分
        ↓
审查交付层
  风险总览 / 双引用 / 修改建议 / 标准条款 / 版本差异 / 审批 / 导出
        ↓
履约运营层
  时间节点 / 义务 / 证据包 / 履约核验 / 补证 / 整改 / 到期与续签
        ↓
企业治理层
  RBAC / 租户隔离 / 知识版本 / 模型路由 / 审计 / 评测 / 成本与监控
```

## 5. 产品优先级

### P0：先解决“可信可用”

1. 建立页级解析质量门禁，持久化每页质量、解析器尝试、选用原因和内容哈希。
2. 统一证据模型，至少包含 `documentId`、`version`、`page`、`clauseId`、`quote`、`startOffset`、`endOffset` 和 `contentHash`。
3. 把时间节点统一为“候选 + 锚点 + 证据 + 状态”；多个基准日期时必须人工选择。
4. 建立真实合同 Golden Dataset，先覆盖服务采购合同，不扩散到过多合同类型。
5. 将重大风险召回率、双引用率、误报率和结构化输出成功率作为发布门禁。
6. 审查结果增加“证据不足”和“有限报告”显式状态，不能与正式通过混淆。

### P1：形成可售卖的审查工作台

1. 建设一页式审查总览：合同摘要、风险等级、重大风险、缺失条款、待确认字段和下一步动作。
2. 风险发现支持 `接受 / 修改 / 申请例外 / 误报 / 待补证`，每次操作记录人员、理由和版本。
3. 每条风险同时展示合同原文、制度/法规依据、影响、建议文本和推荐标准条款。
4. 增加 DOCX 审查意见稿或对照稿导出；PDF 报告作为固定交付物。
5. 增加案件级、版本级问答；默认只回答当前合同和已授权知识，答案必须带引用。
6. 增加合同全局搜索、批量导入、归档分类和重复文件识别。

### P2：做出 AtlasMind 的差异化

1. 完成“合同要求 -> 履约证据 -> Agent 判断 -> 缺口 -> 人工确认”的节点闭环。
2. 增加证据多对多绑定、补证请求、整改记录和历史核验版本。
3. 增加续签、终止、付款、验收等主动工作队列和通知。
4. 用历史人工处置形成“批准例外”和企业谈判偏好，但不得直接覆盖正式规则。
5. 建立风险组合分析：按供应商、合同类型、部门、条款和金额聚合风险暴露。

### P3：企业化与规模化

1. 组织、角色和数据权限：经办人、法务、财务、审批人、管理员职责分离。
2. 单点登录、租户隔离、字段脱敏、加密、审计导出和数据保留策略。
3. 模型网关支持外部 API、客户私有 API 和本地模型；保留按任务路由、熔断和降级。
4. 建立规则、标准条款、法规和 Prompt 的审批发布、版本、生效和回滚流程。
5. 建立服务级指标：成功率、P95 时延、单合同成本、模型调用成本和队列积压。

## 6. 90 天实施路线

以下周期按 3 至 5 名工程人员，并有 1 名兼职法务或采购领域专家估算。

### 第 1-2 周：冻结范围和质量基线

- 只选择“服务采购合同审查”作为首个商业 MVP。
- 收集并脱敏 50 份真实合同，标注 20 份作为第一版金标准。
- 定义证据对象、风险发现、时间节点和人工决定的统一字段。
- 跑通当前 Legacy 与 Graph 的同集对比，记录基线。
- 输出解析失败、引用错误、漏审和误报四类问题榜单。

交付物：评测集 v0.1、基线报告、字段模型、P0 问题清单。

### 第 3-4 周：解析与证据可信化

- 持久化页级解析诊断和 parser 选择记录。
- 明确原始文本、OCR 文本和 canonical text 之间的版本关系。
- 对日期、金额、主体、责任方和引用跨度增加确定性校验。
- 低质量页强制进入人工复核或有限报告。
- 完成表格中的金额、付款节点和验收项抽取最小能力。

验收：所有审查引用都能定位到被冻结的文档版本；低质量解析不会静默进入正式结论。

### 第 5-6 周：审查工作台

- 完成一页总览、风险筛选、双引用查看和逐条处置。
- 增加修改建议、标准条款推荐和处置记录。
- 增加 PDF 报告导出；DOCX 对照稿可在后续迭代。
- 合同问答限定案件、版本和知识范围，并建立引用与拒答门禁。

验收：法务可以从上传合同到完成首轮处置，全程不依赖管理后台和数据库。

### 第 7-8 周：检索与知识治理

- 关键词和向量并行召回，采用 RRF 或经评测的加权融合。
- 按合同版本和条款聚合去重，保留检索来源和排名。
- 法规、制度和标准条款增加来源、效力层级、适用范围、生效/失效时间和版本。
- 建立知识发布审批和历史引用快照。

验收：旧报告始终能看到当时引用的知识版本；新运行使用当前有效版本。

### 第 9-10 周：履约闭环

- 完成时间候选、锚点选择、截止日期计算和人工确认。
- 履约证据绑定到具体义务和要求项。
- 支持补证、重新核验、人工最终判断和不可覆盖的历史记录。
- 建立逾期、待补证、待复核三类队列。

验收：每项结论都展示“要求、证据、判断、缺口”，新证据不会覆盖旧判断。

### 第 11-12 周：试点与发布

- 将真实评测集扩充到至少 100 份合同或 500 个已标注风险点。
- 选 1 个部门进行 Shadow Run，不直接替代现有人工审批。
- 统计法务修改率、误报、漏报、耗时、采纳率和失败原因。
- 完成权限最小闭环、审计导出、故障降级和运维手册。
- 只在指标达标后将 Graph Runtime 切为默认。

验收：完成一次可复盘的真实业务试点，并形成继续投入或收缩范围的决策材料。

## 7. 建议发布门槛

以下均为目标值，需要先记录当前基线，不能直接当作已达到：

| 指标 | 90 天目标 |
|---|---:|
| 支持文件解析成功率 | >= 98% |
| 关键字段原文引用支持率 | >= 98% |
| 重大风险召回率 | >= 90% |
| 风险双引用率 | >= 95% |
| 已标注样本平均误报率 | <= 5% |
| 结构化报告校验通过率 | >= 99% |
| 证据不足时克制率 | >= 95% |
| 人工中断恢复成功率 | >= 99% |
| 试点用户首轮审查耗时下降 | >= 50% |
| 高风险发现被采纳或处置比例 | >= 60% |

模型质量指标和业务价值指标必须同时达标。只提高报告生成成功率，不能说明产品有效。

## 8. 法规与知识库建设建议

知识对象至少补充以下元数据：

- 来源机构和原始链接；
- 文档类型：法律、行政法规、部门规章、地方规定、企业制度、标准条款；
- 适用地区、合同类型和业务部门；
- 发布、生效、失效和废止时间；
- 版本、替代关系和审核人；
- 是否允许作为正式审查依据；
- 每次 Agent Run 实际引用的内容快照。

第一批不要追求法规数量。应先选择与服务采购直接相关的 30 至 50 份高频制度、模板和标准条款，完成结构化、人工审核和评测。

## 9. 商业化表达建议

对外展示不再按“用了哪些 AI 模型”展开，而按用户流程表达：

1. 上传后自动形成可确认的合同档案；
2. 重大风险逐条回到合同原文和制度依据；
3. 一键生成修改建议和标准条款；
4. 审查处置、批准例外和版本变化全程留痕；
5. 签署后自动转为义务、节点和履约证据管理；
6. 用真实指标展示节省时间、风险关闭和逾期降低。

建议产品名称保持 AtlasMind ContractOps，副标题使用“合同风险与履约闭环运营平台”，避免把产品限制为一次性的“智慧评审”。

## 10. 暂时不要做的事情

- 不要同时扩展采购、销售、劳动、租赁、投资等全部合同类型；
- 不要把“支持多个模型”当作首要卖点；
- 不要让多个 Agent 自由辩论来掩盖证据和校验不足；
- 不要让 LLM 直接计算最终风险分或截止日期；
- 不要在缺少真实评测集时宣传准确率；
- 不要自动批准高风险动作、自动确认履约完成或自动给出法律结论；
- 不要先建设复杂大屏，再补审查处置和证据链。

## 11. 下一步立即执行

1. 确认首个试点合同类型为服务采购合同，并确定业务负责人和法务标注人。
2. 从真实合同中脱敏 20 份，建立第一版字段、条款、风险和引用金标准。
3. 用现有评测中心跑出 Legacy 与 Graph 基线，不再以“报告能生成”作为完成标准。
4. 将第 3-6 周的“解析可信化 + 审查工作台”拆成开发任务。
5. 在 30 天评审点决定是否进入法规治理和履约闭环阶段。
