## 1. 为什么要做

不是"加两个按钮"，是现在这条路根本走不通：

| 现状 | 证据 |
| --- | --- |
| 审批接口存在，但没有页面调用 | `/approve`、`/request-revision` 在 `ContractWorkspaceController.java:352-364`；`api/index.js:204` 有封装，全项目无人调用 |
| `待审批` 状态到不了 | 唯一写入点要求先处于 `NEEDS_REVISION`（`ContractCaseServiceImpl.java:1530-1531`），而 `NEEDS_REVISION` 只能从 `PENDING_APPROVAL` 退回——互为前提，形成死循环 |
| 没有"该谁审" | `checkReviewAccess` 只判断"管理员或 REVIEWER 以上"（`ContractAccessPolicy.java:68`），不看部门、不看金额 |
| 状态可被任意改写 | `updateCase` 把 `status` 当普通字段落库（`:937`），无枚举校验、无迁移检查；现实中只能靠 `PUT` 手改状态来"走通"流程 |
| 通过之后没有出口 | `APPROVED` 之后没有任何接口推进到 `SIGNED` / `IN_FULFILLMENT`；全仓库不存在 `SET status='SIGNED'` |
| 阈值没有配置入口 | `sys_setting` 是通用 KV，但 `updateRuntimeSettings` 只认 3 个 key |

## 2. 一句话模型

**案件是一个集合；集合下挂多轮流程；每轮流程是一条带认领的节点链；链上每一次动作都是一条只增不改的事件。**

节点链**线性、无并行分支**：任何时刻只有一个活跃节点。打回是回退，不是分支——它把当前节点标作废，回到前序节点。

进度不是一个 `status` 字段，而是由事件流算出来的。时间轴是事件流的呈现形式，8 阶段只是轴上的里程碑刻度。

## 3. 流程模型

### 3.1 节点链

```text
上传人 ──提交──▶ agent ──出结果──▶ 部门审批 ──通过──▶ 法务 ──通过──▶ 签署（上传人）
   ▲                 │                │                 │                │
   └──── 打回 ───────┴────────────────┴─────────────────┘                │
                                                                          ▼
                                                              签名件一致性核对
                                                        （规则 + agent 提示 + 法务终裁）
```

**用户节点只有三个**：上传人、部门审批、法务。签署节点仍由上传人持有。

`agent` 是**系统节点**，不占人，但它是链上的一环，可以被打回重跑。

### 3.2 节点与认领

每个用户节点上挂一个**候选组**：

| 节点 | 候选组 | 说明 |
| --- | --- | --- |
| 上传人 | 案件的创建人 / 维护人 | 签署节点也归他 |
| 部门审批 | 该部门的审批人池 | 一个部门可以有多个审批人 |
| 法务 | 法务组 | 同上 |

- 节点状态：`待认领` → `处理中`（被认领）→ `已完成`
- **认领后其他人只读**，但可以看到全部留痕
- 认领人不能是"撤回申请人"本人（见 §3.5）

### 3.3 强制确认（上传人节点内部）

agent 跑完不等于可以往下走。上传人**必须**完成两件事，否则"提交部门审批"按钮不可用：

1. 确认合同要素（金额、主体、期限等）
2. 确认履约日程

这两步不是独立节点，是上传人节点内的强制步骤——但仍要逐条留痕，因为后面所有人都要看到"这些数字是人确认过的"。

**合同一变，agent 必须自动重跑**：新版本上传或实质字段（金额/主体/期限/付款条款）变化，自动触发 agent 重新解析与审查，上述两项确认随之作废，必须重新确认后才能再提交。这条是强制的，不是可选项——技术实现见 [phase-2-design §2.8](./phase-2-design.md)。

### 3.4 打回

- **任意节点可以打回到任意前序节点**，不限于上一步
- 打回必须填理由
- 打回产生一条事件，记录 `from_node` / `to_node` / `reason` / `actor`
- 被打回的节点重新进入 `待认领`，其后的节点全部作废（事件保留）

### 3.5 撤回

**通过之后内容锁定。** 想改，只能申请撤回：

1. 申请人（通常是上传人）发起 `撤回申请`，填理由
2. **当前持有者**（该节点认领人）批准或驳回
3. 批准后，**本轮结束、开新一轮**，从申请人所在节点重走（不是在同一轮里回退——否则"批的是哪一版"会被改写）
4. 申请人自己就是当前持有者时，转给管理员批准（避免自己批自己）
5. 撤回申请、批准、驳回，各产生一条事件

### 3.6 取消

取消是"终结本轮流程"，**不终止案件**，不删除任何东西，只标注"已取消"。

允许取消的条件只有两条，**同时满足其一**：

| 条件 | 判定 |
| --- | --- |
| 节点处于 `待认领`，且无人处理已满 **6 小时** | 超时自动可取消 |
| 流程卡在 agent 失败 | `agent_run.status=FAILED` |

- 不满足条件时，取消按钮**置灰**，并在按钮旁写明原因（"当前有认领人正在处理" / "待认领尚未满 6 小时"）
- 取消必须通知**全部参与者**
- 取消后**不能重开**；同一版本也不能复活。要重做就**换版本重新上传**，在同一案件集合里开新的一轮

判定条件与落库方式见 [design §2.4](./phase-2-design.md)。

### 3.7 签署确认

法务通过 → 签署节点（上传人持有）→ 上传签署件：

1. **规则硬校验**：按 [design §4](./phase-2-design.md) 的五条规则（哈希/页数/条款编号/关键字段/相似度）比对审批版本
2. **agent 提示**：语义级差异（新增责任限制、把"应当"改成"可以"），只输出"疑似不一致 + 位置 + 证据"
3. **法务终裁**：人工确认，agent 不作为唯一判定

核对结果不一致时，**由上传人二选一**：

- **重走审批**：开新轮次，内容重新审
- **放弃**：记录事件，本轮结束，案件保留

签署节点允许写：签署件、签署日期、生效日期、我方签署人。这些**不触发重审**。

## 5. 与原方案相比变了什么

| v0.2 | v0.3 |
| --- | --- |
| 按金额阈值自动算审批人（角色 → 人） | **阈值废弃**：所有合同都经法务，审批人来自预配名单 |
| 13 个 `status` 表达进度 | 事件流表达进度，`status` 只是汇总 |
| 8 个阶段并列 | 3 个用户节点 + agent 系统节点 |
| 要素确认、日程确认是独立阶段 | 降为上传人节点内的强制步骤 |
| 风险处置是法务的活 | 全员可见可改，改动留痕，可打回 |
| 审批记录一张表 | 六张表：轮次、节点、事件、认领、撤回、签署核对 |
| 无取消 | 取消有严格条件，灰按钮写原因，不可重开 |

## 8. 验收雏形

1. 上传人提交 → agent 跑完 → 未确认要素前"提交部门审批"不可用
2. 部门审批人 A 认领后，B 只能看不能操作，且能看到 A 的动作留痕
3. 法务跨节点打回给上传人，事件流完整显示往返，理由可见
4. 通过后修改金额被拒；申请撤回 → 持有者批准 → 流程回到申请人节点
5. 待认领满 6 小时，取消按钮由灰变亮并通知全员；处理中取消按钮保持灰色且有原因
6. 取消后案件仍在，标注"已取消"，不能重开；换版本重新上传可开新轮次
7. 签署件与审批版本不一致：规则命中 + agent 提示 + 上传人二选一（重走 / 放弃）
8. 一期页面每个阶段都有真实进入时间，与事件记录一致
9. 时间轴按时间排序展示全部动作（打回 / 认领 / agent 运行 / 修改 / 撤回 / 取消），可展开看明细

## 9. 风险

- **状态机没落地就先做审批** → 必然返工。二期第一件事是建流程表与事件表，不是画按钮。
- **审批权限与现有成员角色（OWNER/EDITOR/REVIEWER/VIEWER）是两套语义**，需明确映射，避免"是 REVIEWER 但不是审批人"的歧义。
- **取消成了逃生门**：条件不严格就会变成"换个审批人试试"。6 小时 + 通知全员是底线，不能放宽。
- **agent 结果被多人反复改**：改动留痕容易，但"哪一版是最终确认版"要有唯一指针，否则审批结论无法绑定版本。
