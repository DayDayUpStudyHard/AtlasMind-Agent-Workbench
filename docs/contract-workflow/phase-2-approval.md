## 1. 为什么需要这一期

不是"加两个按钮"，而是现在这条路根本走不通：

| 现状 | 证据 |
| --- | --- |
| 审批接口存在，但没有页面调用 | `/approve`、`/request-revision` 在 `ContractWorkspaceController.java:340-358`；`api/index.js:204` 有封装，全项目无人调用 |
| `待审批` 状态几乎到不了 | 全项目只有一处写 `PENDING_APPROVAL`，条件还卡着 `WHERE status='NEEDS_REVISION'`（`ContractCaseServiceImpl.java:1521-1526`） |
| 没有"该谁审" | `checkReviewAccess` 只判断"管理员或 REVIEWER 以上"（`ContractAccessPolicy.java:68`） |
| 状态可被任意改写 | `updateCase` 把 `status` 当普通字段落库，无枚举校验、无迁移检查（`ContractCaseServiceImpl.java:931-951`） |
| 阈值没有配置入口 | `sys_setting` 是通用 KV，但 `updateRuntimeSettings` 只认 3 个 key，管理端 `Settings.vue` 是写死表单 |

## 2. 目标

让"待审批"能真正走完：**知道该谁审 → 能通过或退回 → 全程留痕 → 退回有明确去处**。

## 5. 设计要点（草案）

### 5.1 审批人怎么算

按 PRD §3：

```text
amount ≤ 阈值A           → 部门负责人
阈值A < amount ≤ 阈值B   → 部门负责人 + 法务负责人
amount > 阈值B           → 部门负责人 + 法务负责人（法务负责人终审）
阈值缺失 / 部门无人      → 不猜，返回 NO_APPROVER，页面提示联系管理员
```

- 阈值存 `sys_setting`（新增两个 key），**管理端可改**，改动写操作日志。
- 只读计算，不在案件表里冗余存审批人；改派以审批记录为准。

### 5.2 审批记录（字段草案）

`id / case_id / stage / round / approver_role / approver_id / action / comment / target_version / created_at`

- `action`：`APPROVE` / `REJECT` / `REASSIGN`
- `target_version`：审批针对的文档版本 + 产物版本，保证"审的是哪一版"可回答
- 记录只增不改（改派也是新增一条）

### 5.3 接口（草案）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| POST | `/contracts/{id}/approve` | 已有，补记录写入与版本校验 |
| POST | `/contracts/{id}/request-revision` | 已有，补 reason 必填、补记录 |
| GET | `/contracts/{id}/approvals` | 新增，审批链 |
| POST | `/contracts/{id}/approvals/{id}/reassign` | 新增，改派 |

### 5.4 前端

- 案件详情 ⑤ 阶段展开后显示：审批链（当前到谁 / 历史）、通过、退回（弹窗必填理由）。
- 一期工作流条不动；`stage` 仍是 `RISK_DISPOSAL`，只在其内部细分"待处置 / 待审批 / 已批准"。
- 「下一步」卡片在待审批时，按钮由 `APPROVE` 类型驱动，仅审批人可见可点。

### 5.5 状态机修正

- 审查完成且无 OPEN 发现 → `PENDING_APPROVAL`（不再要求先经过 `NEEDS_REVISION`）。
- `updateCase` 不再接受任意 `status` 写入；状态只能经由显式动作变更。
- 全部迁移集中到一处实现，作为第 2 层的唯一真源。
- **每次阶段变更写入阶段事件**（阶段 key、进入时间、操作人），供一期接口的 `enteredAt` 填充。这是二期必须交付的一项；不做则一期的"停留时长"永久为空，第 5 层看板也无从计算。

## 6. 与一期的衔接

- 一期接口返回的 `stages[]`、`stage` 枚举不变，二期只填 `actorName` 与新增 `approvals[]`。
- 一期 `enteredAt` 为 `null` 的阶段，二期由阶段事件填充；前端不改。
- 一期望时文案"审批功能建设中"在二期删除。

## 7. 验收雏形

1. 30 万合同：提交后待审批人 = 部门负责人；50 万以上：加出现法务负责人。
2. 审批人登录后能看到待办，能通过；非审批人看不到按钮（或按钮不可点且有提示）。
3. 退回必填理由，退回后按 §4-1 的规则回到指定阶段，历史记录完整。
4. 改派后原审批人失去权限、新审批人收到待办，两条记录都在。
5. 阈值在管理端修改后，新提交的合同按新阈值判定；历史合同不受影响。
6. 无法确定审批人时：不卡死、不猜，页面显示 `NO_APPROVER` 与处理办法。
7. 每个阶段有真实进入时间；一期页面的"已停留"与阶段事件记录一致，且不再为空。

## 8. 风险

- **状态机没落地就先做审批** → 必然返工。二期应把"修状态机"当第一件事，而不是顺带。
- 审批权限与现有"成员角色"（OWNER/EDITOR/REVIEWER/VIEWER）是两套语义，需明确映射，避免出现"成员是 REVIEWER 但不是审批人"的歧义。
