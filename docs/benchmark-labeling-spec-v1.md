# ContractOps Benchmark Labeling Specification v1

## Purpose

This specification defines the private, reviewable gold labels used to assess
the five production ContractOps capabilities: first intake recognition,
contract element extraction, timeline extraction, risk review, and fulfillment
verification. A candidate label generated by an LLM is evidence for human
review, never production ground truth by itself.

## Corpus policy

- `benchmark-private/` is intentionally ignored by Git. It may contain real
  contracts, extracts and candidate labels.
- The tracked repository may contain anonymized examples and this schema, but
  never a real contract's title, parties, account numbers, contacts, or text.
- Every source record stores a content SHA-256 and its source case/document ID
  locally. Hashes provide reproducibility without publishing contract text.
- Corpus distribution for core-v1 is 36 contracts: 18 engineering/EPC, 7
  service, 5 goods procurement, 4 software/IT, and 2 other agreements.
- Where an eligible local source contract is unavailable, a record is marked
  `SYNTHETIC_EXTENSION`; it is not represented as an observed production
  contract.

## Review lifecycle

`PROVISIONAL` means incomplete or manually entered. `CANDIDATE` means an LLM
or deterministic generator produced a structured proposal. `APPROVED` means a
reviewer compared the proposal to the contract and accepts it as the golden
answer. Only `APPROVED` cases count toward a release gate; candidate cases may
run in observation mode and expose quality regressions.

## Schema v2

Each file-backed dataset has a `manifest.yaml` with `schemaVersion: 2`,
`taskType`, `labelStatus`, `privateCorpus`, and a `profile` describing the
strata. Each case has `caseId`, `contractText`, `taskType`, `annotationStatus`,
and a task-specific `expected` mapping.

### First intake recognition

`expected.intakeFields` is a list of `{title, key, value, kind}`. Required
`kind` values are `title`, `party`, `partyRole`, `amount`, `date`, and
`contractNumber` when they appear in the source. Amount labels include the
currency and normalized Chinese/Yuan representation.

### Contract element extraction

`expected.elements` is a list of `{title, elementKey, category, value}`. It
contains only fields that are materially present in the text, plus explicit
absence entries such as `开工日期:缺失` where an absence is meaningful. Dynamic
industry-specific fields are allowed; do not force engineering fields onto an
IT contract.

### Timeline extraction

`expected.timelineNodes` is a list of `{title, nodeType, responsibleParty,
condition}`. `title` uses `节点名称:日期或条件说明`. Fixed dates use ISO
`YYYY-MM-DD`; conditional events must say `条件事件` and must not invent a date.

### Risk review

`expected.risks` is a list of `{title, severity, riskDimension, keyTerms,
mustHaveContractCitation, mustHavePolicyCitation}`. A risk must be specific to
the contract text and a known applicable rule or standard. A missing clause is
labelled only when the rule is applicable to the scenario.

### Fulfillment verification

`expected.fulfillment` is a mapping containing `requirements`, `judgements`,
and `manualResult`. Evidence must be saved separately from contract text.
`manualResult` is the controlled human decision used when resuming the graph;
the model must not auto-confirm fulfillment.

## Quality checks

- Every required label has a source quotation or a source location note in the
  reviewer worksheet.
- Candidate labels must preserve uncertainty rather than fill missing values.
- A case with OCR noise retains both the source text and a noise-level tag.
- Two reviewers resolve disagreements on amount, parties, dates, risk severity,
  and fulfillment conclusion before status becomes `APPROVED`.
- A release dataset requires at least 10 approved cases per task in v2. The
  first corpus should reach 24+ approved cases per core task before threshold
  tuning.
