结论：现有 LangGraph 架构可以继续用，不需要推倒重写。准确度瓶颈主要是“检索结果是否完整、证据是否真正支持结论、缺失条款能否可靠判定”，不是 Agent 数量不足。
当前关键问题
重排序还不够强
当前已经做了向量检索、ES 关键词、MySQL 关键词和 RRF 融合，这是对的。但最终排序仍以关键词命中奖励为主，并不理解“该条款是否回答当前审查问题”。见 [contract_store.py (line 223)](D:/Project/AtlasMind Agent Workbench/tools/chat-assistant/backend/app/agent_runtime/contract_store.py:223)。
建议增加真正的 reranker：
先召回 30～50 条。
用轻量 cross-encoder 或 LLM rerank 排到 8～12 条。
排序依据包含：问题相关性、条款完整性、主体和条件是否匹配、是否属于同一章节。
合同条款与知识库条款分别排序，不能混在一起竞争名次。
这是目前性价比最高的准确度改进。
补充检索没有重新形成风险结论
当前覆盖不足后会执行 targeted_retrieval，但随后直接生成“范围受限报告”，没有把新证据重新送回领域分析和结论校验。见 [contract_review.py (line 117)](D:/Project/AtlasMind Agent Workbench/tools/chat-assistant/backend/app/agent_runtime/graph/contract_review.py:117)。
正确链路应为：
覆盖不足
→ 针对缺口重新生成查询
→ 补充检索
→ rerank
→ 只重新分析缺失领域
→ 再次验证
→ 完整报告或范围受限报告
这个属于 P0，因为现在第二次检索即使找到了关键条款，也不能真正修正风险发现。
“合同缺少某条款”的判断不够严格
目前检测到“缺少、未约定、未发现”时只是添加警告，并不会阻止结论发布。见 [validation.py (line 80)](D:/Project/AtlasMind Agent Workbench/tools/chat-assistant/backend/app/agent_runtime/graph/nodes/validation.py:80)。
负向结论必须经过更严格流程：
检查完整条款目录。
使用同义词、反向表达、章节类型进行多路检索。
检查相邻条款、附件和专用条件。
仍找不到才能输出“可能缺少”。
检索覆盖不足时只能输出“暂未确认”，不能说“合同未约定”。
覆盖度目前偏“计数型”
一个领域只要有证据、有一条发现，就可能被标记为 COVERED。但“价款、付款与税务”实际包含金额、税率、付款条件、发票、结算、扣款、逾期责任等多个必查子项。
应改为检查项矩阵：
领域
→ 必查子项
→ 是否适用
→ 是否检索到合同证据
→ 是否检索到知识依据
→ 是否形成结论
→ 未覆盖原因
领域全部适用子项完成后才能标记“已覆盖”。
风险领域规划看到的合同不完整
动态领域规划目前只读取前 80 个条款的短片段。长合同后半部分、附件、专用条款可能没有进入规划上下文。见 [domain_tasks.py (line 84)](D:/Project/AtlasMind Agent Workbench/tools/chat-assistant/backend/app/agent_runtime/graph/nodes/domain_tasks.py:84)。
建议使用“分层合同地图”：
一级：章节目录和条款类型分布。
二级：每章摘要、金额、日期、责任主体等信号。
三级：按领域检索完整条款。
附件和专用条件单独标记优先级。
这样不需要把全文塞给模型，也不会只看合同前半部分。
时间节点仍有候选数量上限
目前最多复核 24 个候选。超长合同可能直接漏掉后面的有效节点。见 [config.py (line 54)](D:/Project/AtlasMind Agent Workbench/tools/chat-assistant/backend/app/config.py:54)。
不应直接截断，应先做确定性去重和优先级分类，然后分批复核全部候选。预算不足时可以延迟处理低优先级候选，但不能静默丢弃。
评测集不足以衡量准确度
当前只有 3 个合成案例，而且风险召回主要靠标题字符串匹配。average_risk_precision、schema_valid_rate 等字段虽然定义了，但没有真正计算。见 [metrics.py (line 10)](D:/Project/AtlasMind Agent Workbench/tools/chat-assistant/backend/app/agent_runtime/evaluation/metrics.py:10)。
建议至少建设：
50～100 份脱敏真实合同起步。
覆盖服务、采购、工程、软件、NDA 等类型。
标注合同要素、时间节点、风险、引用证据和“不应发现”的风险。
分别评估检索 Recall@K、要素 F1、时间节点召回率、风险准确率、引用支持率、延迟和 Token。
按合同版本固定回归，避免改提示词后旧问题重新出现。
多 Agent 怎么用
建议采用“受控多 Agent DAG”，不采用多个 Agent 自由讨论：
合同地图 Agent
→ 领域规划 Agent
→ 多个领域审查 Agent 并行
→ 证据核验 Agent
→ 冲突裁决 Agent
→ 确定性质量门禁
→ 人工确认
领域审查 Agent 可以并行，但只允许输出结构化主张：
合同事实 → 知识依据 → 差异判断 → 可能影响 → 修改建议
证据核验 Agent 不重新写报告，只判断：
引用是否真的支持主张。
是否漏读限制条件、例外和相邻条款。
严重程度是否被夸大。
“明确约定”和“AI 推断”是否混淆。
以后接第二模型时，只需增加 VerifierAdapter。优先让第二模型核验高风险、低置信度和多路检索冲突项，不必把所有结果重复跑一遍。
推荐实施顺序
P0：真实 reranker、修复补充检索闭环、负向结论门禁、扩充评测集。
P1：子项级覆盖矩阵、分层合同地图、相邻条款和附件检索、冲突裁决。
P2：独立核验 Agent、可选第二模型、基于人工修改记录做主动学习。
性能优化：页面级低质量 OCR 重试、检索缓存、查询 embedding 缓存、要素包并行处理、只重跑受影响条款。
准确度优先时，我最建议先做 P0。它比增加一批自由协作 Agent 更能稳定提升结果，也更容易通过评测证明效果。当前未修改代码。
